Test bench

Tests run on 19 September 2026 · by Guillem Sánchez

Almost everything written about codecs and video editors gets repeated from site to site without anyone checking it. This page is the opposite: seventeen files built on purpose, one per container and codec combination, run through the same chain of commands VidToFLAC executes, with every result measured.

If anything here contradicts another page on this site, this one wins. And if you get a different result, write to me and I will run it again.

What it was tested on

  • FFmpeg 6.1.1 (Ubuntu package 6.1.1-3ubuntu5), the same engine VidToFLAC compiles to WebAssembly.
  • DaVinci Resolve Studio 21 on Ubuntu, for the part that has to be checked inside the editor.
  • Six-second test files, with synthetic 640×360 video and a 440 Hz tone, generated on the spot. Nothing is downloaded from anywhere: every file is built with FFmpeg from scratch.

How each file is built

One example, the MP4 with AAC audio that stands in for any camera, phone or OBS recording:

ffmpeg -f lavfi -i testsrc2=s=640x360:r=30:d=6 -f lavfi -i sine=f=440:d=6:sample_rate=48000 \
       -c:v libx264 -preset veryfast -crf 20 -c:a aac -b:a 192k -shortest source.mp4

That file then goes through the decision the tool makes: if the video codec is on its list of codecs the browser cannot decode, it is re-encoded to H.264; otherwise it is copied. The audio always becomes FLAC.

ffmpeg -i source.mp4 -c:v copy -c:a flac output.mkv          # video codec the browser can decode
ffmpeg -i source.mp4 -c:v libx264 -preset ultrafast -crf 18 -c:a flac output.mkv   # one it cannot

What the numbers show

  • What the browser can read and what the editor can read are not the same list. H.264, AV1 and MPEG-4 (Xvid) are copied. Nine are re-encoded to H.264: WMV2, MPEG-2 and HEVC because browsers cannot decode them, and VP8, VP9, H.263, Theora, FLV1 (Sorenson) and MS MPEG-4 v3 (DivX 3) because DaVinci Resolve does not play them properly when they arrive copied. With Xvid the picture is left alone, even though the browser cannot always show you a preview.
  • Converting to FLAC almost always makes the file bigger. Starting from lossy audio, every output grew: the MP4 with AAC went from 807 KB to 1,019 KB. What you gain is compatibility, not size.
  • Unless the source was already lossless. The MOV with PCM dropped from 1,255 KB to 765 KB, and the standalone WAV from 563 KB to 85 KB, because FLAC compresses what PCM stores raw.
  • A FLAC input comes out identical, byte for byte: 85 KB before and after. The tool does not recompress it.
  • Re-encoding the video multiplies the size. The HEVC MP4 went from 491 KB to 2,458 KB — five times larger, because H.264 needs far more bitrate for the same quality. That is the price of a preview the browser can play.
  • AC-3, E-AC-3, DTS and AMR all decode fine. The four formats editors usually refuse were converted to FLAC without trouble.

How much FLAC really compresses

It depends entirely on the material, which is why a measured range beats a single percentage. Over 39.5 seconds of stereo audio at 48 kHz and 16 bits, always starting from a 7.58 MB WAV:

  • White noise (the worst case there is): 3.56 MB, 53 % of the original.
  • A pure 440 Hz tone: 540 KB, 7 %.
  • A real screen recording, with silences and speech: 431 KB, 6 %.

Music and continuous speech sit between those extremes, usually closer to half than to 6 %. Anyone promising you a fixed percentage has measured nothing.

What has been tested inside DaVinci Resolve

This is the part that cannot be automated. On 20 September 2026 I imported all seventeen files, one by one, into DaVinci Resolve Studio 21.0.4 build 5 on Ubuntu — first the originals, then the converted ones. Here is what came out.

Of the seventeen originals, only three were usable: the ones carrying MP3, PCM and FLAC. The other fourteen failed in four distinct ways, and the difference between them matters more than it looks:

How it failsWhat you seeAudio codecs
Silent trackThe audio track appears, but nothing playsAAC-LC, in all four files where it appears
No track at allThe clip imports with video onlyOpus, Vorbis, E-AC-3, DTS
Decodes wronglySomething plays, but not what is in the fileAC-3
Will not importThe file never reaches the Media PoolAVI (Xvid), WMV, VOB, 3GP

The silent track is the worst of the four, because the clip looks fine and you go hunting for the problem in the project settings. The AC-3 case was a surprise: I checked with FFmpeg that the source file is a constant 440 Hz tone from start to finish, so the odd beep that comes out halfway through is the decoder's doing, not the file's.

Sorted out, the pattern explains itself: what is free of patents gets through, and what is not does not. FLAC, PCM and MP3 — whose patents expired in 2017 — import fine; AAC, AC-3, E-AC-3, DTS and WMA do not. And this is the paid edition, with every licence Blackmagic ships: paying does not fix it, at least on Linux.

With the seventeen converted files, all seventeen import and fifteen play. The four that Resolve refused outright now open without trouble; the AC-3 stops sounding wrong; the AAC stops arriving silent.

The two that stayed silent, and why the tool changed

The two remaining failures were the MKV with VP9 video and the WebM with VP8: correct picture, silent FLAC track — the same FLAC track that plays fine in the other fifteen files. To isolate the cause I repeated both with the audio copied bit for bit and the video codec as the only change, now H.264. Both played.

So: the video codec inside the MKV decides whether Resolve plays the audio. Testing the other codecs the tool used to copy turned up four more with a related problem — Theora, FLV1 (Sorenson), MS MPEG-4 v3 (DivX 3) and the H.263 in the 3GP — which import with sound but no picture.

That is why VidToFLAC no longer copies those six: VP8, VP9, H.263, Theora, FLV1 and MS MPEG-4 v3 are re-encoded to H.264, even though browsers read them perfectly well. It costs time and file size — the three matching rows in the table above show it — but the file that comes out is usable in an editor, which is what the tool is for.

AV1 is still copied, and that deserves its own line: it is what many modern screen recorders produce, re-encoding it would be the most expensive job of all, and Resolve turns out to open it with picture and sound untouched. H.264 and MPEG-4 (Xvid) are copied too, and work just as well.

What is not tested yet

For honesty, because a test bench that hides its gaps is worth nothing:

  • The same tests on Windows and macOS, where AAC and MP3 support is licensed.
  • The free edition of Resolve on Linux, as against Studio. Everything above is Studio: it says nothing about what the free edition does, not even with AV1 or HEVC.
  • Long files and real camera footage, to find the browser's memory ceiling.
  • One oddity I could not reproduce: the converted WMV came out silent the first time and started halfway through on the second play. The file is correct; this needs repeating before anything is claimed about it.

How to repeat the tests

All of this reproduces with FFmpeg and ffprobe on any machine. Build the file with the first command, convert it with the second, then check what came out:

ffprobe -v error -show_entries stream=codec_type,codec_name -of default=nw=1 output.mkv

If your result does not match the table, I want to know: send your FFmpeg version and the exact command through the contact form.

More on how everything here gets verified is on the author page. And if what you need is to fix your file right now, the tool is on the home page.

All processing happens on your device using ffmpeg.wasm — no data ever leaves your browser.
